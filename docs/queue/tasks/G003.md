## Brief
The main suite (`:desktop:crossroadsTest`) is green, but the older `:desktop:test` group has 14 failures that went stale as the
town changed under them (the new planned capital, a "grounds" district, sprite landmarks replaced by hand-made models):
- `TownWalkTest`, `TownPlaceTest`, `TownMapTest`, `StreetPropRulesTest`, `RailNetTest`, `OpenWalkTest` (12 fail on
  ccr-52e43ebb-xnmj2e before the latest intake);
- `RailNetTest.ridesFollowTheTrackAtWorldScale`: gamma's track now rounds the grounds district and the west ride turns
  at cos -0.55 against a -0.5 limit;
- `TownWalkTest.everyTransitionWorksBothWays`: the grounds' street rows are ~11,000 units long, so the walk times out.

For each failure, find out whether the **test** is stale (it pins numbers, names or a layout the planned town changed)
or the **code** is wrong (a real bug the test caught):
- Stale test: re-derive the expectation from the current rules (read kotlin-street/docs/TOWN_PLAN.md and the code), never
  just loosen a number until it passes. Say why each change is right.
- Real bug (e.g. the rail track really making a too-sharp turn, or a transition that really doesn't work both ways):
  don't change shared code yourself; write it up in DELIVERY.md with the evidence and leave that test failing, marked
  with a clear `@Ignore("bug: <one line>, see DELIVERY.md")` only if it blocks the rest.

**Skip `TownWalkTest` and `StreetPropRulesTest`.** They test the classic street view, which the cleanup plan
(docs/CLEANUP_PLAN.md) deletes. Work on the live ones: `TownPlaceTest`, `TownMapTest`, `RailNetTest` and `OpenWalkTest`.
